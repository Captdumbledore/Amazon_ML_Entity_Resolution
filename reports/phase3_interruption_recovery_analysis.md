# Phase 3 Interruption Recovery Analysis

## 1. Project State After Restart
The Phase 3 character n-gram retrieval experiment was interrupted during the execution of the `(3, 5)` n-gram configuration while processing the US country data (around batch 160). The script did not finish naturally, and no final metrics or reports were generated.

## 2. Files/Artifacts Found
The only artifact generated by Phase 3 found in the workspace is:
- `data/phase3_candidates_3_5.parquet` (approx. 255 MB)

Files expected upon completion but **NOT found**:
- `reports/phase3_ngram_retrieval.md`
- `reports/phase3_ngram_metrics.csv`
- `data/phase3_candidates_3_6.parquet`

## 3. India Result Recovery Status
The India results were written as row groups into `data/phase3_candidates_3_5.parquet`. However, because the script was interrupted abruptly, `writer.close()` was never called. This means the Parquet file's footer (which contains essential metadata, schema, and row group locations) was never written. The file is therefore structurally corrupted (`Parquet magic bytes not found in footer`). While advanced PyArrow data-recovery tools might salvage the row groups, the data is not immediately usable.

## 4. US Result Recovery Status
The completed US batches (1–160) are in the exact same state as the India results. They exist in the 255 MB corrupted Parquet file but cannot be natively read without manual low-level file recovery. 

## 5. Checkpoint/Resume Capability
The current implementation in `src/ngram_retrieval_experiment.py` has **NO** checkpointing or resume capability. 
- It opens the Parquet writer at the beginning of the `generate_candidates` function and overwrites any existing file with the same name.
- It processes countries and batches sequentially without tracking progress on disk (other than printing to stdout).

## 6. Exact Last Safely Persisted Computation
There is **no** safely persisted computation. All generated candidates are trapped inside the corrupted Parquet file.

## 7. Whether Recomputation is Required
Yes. With the current codebase, recomputation is required because the script cannot read the corrupted file or append to it. If run as-is, the script will overwrite the 255 MB file and start from India all over again.

## 8. Whether Batch-Level Resume is Possible
Batch-level resume is **not possible** with the current code. The code does not check for previously completed batches or countries.

## 9. Potential Corruption/Incomplete-Output Findings
- `data/phase3_candidates_3_5.parquet` is definitively corrupted due to a missing footer. Attempting to read it via `pandas.read_parquet()` or `pyarrow.parquet.read_table()` throws an `ArrowInvalid: Could not open Parquet input source: Parquet magic bytes not found in footer` exception.

## 10. Computational Bottleneck Observed
The huge runtime (and memory usage) is caused by the sparse TF-IDF matrix multiplication and row-wise top-K sorting in the `get_top_k` function combined with the batch processing loop:
1. **Expensive Sparse Dot Product:** `sim = s1_batch_tfidf.dot(targets_tfidf.T)` computes the cosine similarity of 1,000 S1 entities against all 6.18 million US targets at once. Even though it's sparse, the sheer size of the vocabulary (1.39M) and the number of targets results in a massive number of non-zero calculations and a large intermediate matrix `sim`.
2. **Python-Level Loop Overhead:** The `get_top_k` function iterates row-by-row in Python (`for i in range(sim.shape[0]):`) and performs `np.argsort` or `np.argpartition` on the underlying NumPy arrays. Doing this for millions of entities over thousands of batches introduces significant overhead compared to a vectorized top-K or a highly optimized similarity search engine.

## 11. Recommended Next Action
**DO NOT RUN THE SCRIPT AS-IS.** 
Before restarting the experiment, the `src/ngram_retrieval_experiment.py` script must be modified to:
1. **Implement Checkpointing:** Save candidates periodically in a way that is robust to interruptions (e.g., writing smaller, separate Parquet files per country or per chunk of batches, which can be combined later).
2. **Optimize Retrieval:** Address the computational bottleneck. Options include chunking the target matrix as well, using an optimized library for sparse top-K search (e.g., `sparse_dot_topn`), or adjusting the TF-IDF parameters to increase sparsity (e.g., reducing `max_df` or increasing `min_df`).
